## Purpose

Where [[B5. Translate Requirements to Areas of Expertise and Define JD Groups]] maps the Job Description to the candidate's own skills framework, this step interprets and prioritises the Job Description in its own language — extracting what the role actually demands, ranked by importance, and recording each requirement as a discrete, scoreable line item.

**This step now runs first in the B phase** (CI · *Lead Page as Pipeline Canvas* §2.1 — it was B5). Two reasons, and the weaker one came first: the Lead page's Map needs requirements early to have anything to draw. The real reason is that [[B5. Translate Requirements to Areas of Expertise and Define JD Groups]] is *called* "Translate Requirements" and used to run before any requirements existed — so it necessarily translated the raw JD instead, and its title and its position contradicted each other. Extraction-first resolves that. Second, hard dependency: [[B3. Identify Roadblocks]] can attach a roadblock to a specific requirement row, which is impossible if the rows don't exist yet.

This step is primarily executed as a preparatory step for [[B6. Role Fit & Investment Worthiness Score]].

Output feeds the `job_requirements` table — one row per requirement. See Section D for what is written and by which path.

---

## A. Source

The job description is supplied **inline, in the message you are given**, under the heading `JOB DESCRIPTION:`. That text is the complete and only source for this step.

Do not attempt to open, fetch, or look up a file, a workbook, a SharePoint list, or any other external location — you have no access to one, and nothing outside the supplied text is needed. If the supplied text looks shorter than a full posting, extract from what is there rather than treating the source as missing: returning an empty result because the source appeared absent is a failure, not a valid answer.

> Historic note (superseded): this step previously read a `.md` file from `OneDrive > Obsidian Vault > JobSearch Camunda > Job Descriptions`, back when it ran through the Microsoft 365 connector. The app now passes the JD directly.

## B. Priority Groups

Each requirement is classified into one of three groups:

| Requirement Group | Definition |
|---|---|
| Core | Explicitly mandatory. The JD uses language such as "required", "must have", "essential", or positions it as a primary responsibility or qualification. Missing this requirement is a likely screen-out. |
| Important | Strongly preferred or frequently emphasised. The JD uses language such as "preferred", "strong advantage", "ideally", or repeats the theme across multiple sections. |
| Nice-to-Have | Optional, supplementary, or bonus. Mentioned once without emphasis, or framed as "a plus", "desirable", or "would be beneficial". |

**Ranking within groups:** within each group, requirements are numbered sequentially starting at 1 (`Rank`). The `Requirement Order` is a sequential global counter across all groups for the lead (Core first, then Important, then Nice-to-Have).

## C. Extraction Rules

1. Extract requirements from the entire JD — responsibilities, qualifications, requirements, and experience sections all contribute.
2. Each requirement should represent one distinct, addressable demand — not a section header or generic filler phrase.
3. Write the `Requirement` as a short descriptive label (5–10 words, title case).
4. Write the `Requirement Description` in the JD's own words or a faithful close paraphrase — never in the candidate's language.
5. **`Source Text` — the verbatim source, and it is not the same field as `Requirement Description`.** Copy the exact sentence (or the smallest contiguous span of sentences) from the JD that this requirement was drawn from, character for character: no tidying, no trimming to fit, no joining fragments from different parts of the posting, no translation. Rule 4 permits a close paraphrase; this field permits none — a paraphrase is *your reading of* the source, and the Map quotes the posting back to the user so they can see the actual words the requirement came from. If a requirement genuinely synthesises several separated lines, quote the single most load-bearing one rather than stitching a sentence the posting never contained. Leave it empty only if the requirement is implied by the posting's structure rather than stated in any sentence.
6. **Skills column.** Capture the key skills, competencies, or capabilities **as described or implied in the Job Description**, using the Job Lead's own language and terminology whenever possible (especially for Core and Important requirements). This column reflects **what the role is asking for** — it is JD-facing only, not a lookup against your own profile.
7. Aim for completeness over brevity — better to over-extract and consolidate than to miss a requirement that drives scoring.
8. **Language note:** 
	1. JDs written in German are extracted in German (`Requirement Description` may remain in German).
	2. The `Requirement` label should be written in English for consistency.


> [!Note]
> `Requirement Skills` is not matched against your own Skills/Competences/Attributes at this stage — that correspondence is established later, at [[C2. Map JD Requirements to Supporting Evidence]], when this requirement is paired with a specific piece of your evidence (a STAR action, responsibility, or bullet). That evidence item's own tags become **My Skills** for the pairing. C4 and C5 work from that C2-level pairing, not from anything decided here.

## D. Persistence

This step emits a single `emit_requirements` tool call. The app validates it
(`lib/llm/schemas.ts` → `B2.zod`) and writes **one `job_requirements` row per requirement**
(`lib/pipeline/screening.ts`). No standalone output, export or table is produced — do not generate one.

Where each field lands:

| Tool-call field | Column |
| --- | --- |
| `order` | `requirement_order` — the global counter |
| `groupRank` | `group_rank` — the counter **within** the group (§B calls this "Rank") |
| `rank` | `rank` — holds the **group name**: `Core`, `Important` or `Nice-to-Have` |
| `requirement` | `requirement` |
| `description` | `description` |
| `sourceText` | `source_text` |
| `skills` | `skills` |

Two things this step must not do:

- **Do not invent a requirement to reach a count.** The app re-asks when an extraction comes back
  implausibly thin for the length of the posting, and throws rather than writing a bad set. Padding
  defeats that guard by making a thin reading look complete.
- **Do not emit placeholder or example values.** Every field must carry real content drawn from this
  posting. A field with nothing genuine to say is left empty; it is never filled with a description of
  what should go there.

The `Initial_*` fields (match strength, key strengths, missing/weak, score) are **not** yours — they
are written later by [[B6. Role Fit & Investment Worthiness Score]] onto these same rows.

*Historic (superseded): this step previously produced a per-JD requirement block as a markdown table
with a `Requirement_Line` cross-reference, plus an end-of-batch tab-delimited SharePoint export
rendered as an interactive HTML widget with a Copy button, back when it ran through the Microsoft 365
connector. `Requirement_Line` is composed for display now and never stored.*
