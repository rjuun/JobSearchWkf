## Purpose
Map every requirement extracted in Step [[B2. Extract Requirements from Job Description]] to a specific, verifiable evidence from the candidate’s background.
This step creates the traceability foundation required for writing truthful, ATS-optimized CV bullets, Skills and Profile in subsequent steps (C3, C4, and C5).

The result links each Job Description requirement to the exact source of evidence (STAR actions, Responsibilities, Bullets, Education, or Languages) and indicates where the corresponding bullet should appear in the CV.

---

## A. Source and Execution Sequence

Everything this step needs is **supplied inline, in the message you are given**:

- `CANDIDATE EVIDENCE (cite by exact ref code):` — the candidate's whole evidence graph, one line per item, each already labelled with its kind and its stable ref code.
- `ROLE:` and `REQUIREMENTS (map each by its number):` — the Core and Important requirements for this lead, numbered.
- `CV POSITION SLOTS` — the exact set of labels you may assign.

Do not attempt to open, fetch, or look up a file, a workbook, a SharePoint list, or any other external location — you have no access to one, and nothing outside the supplied text is needed. **The evidence listing you were given is the complete universe of citable evidence:** if something is not in it, it does not exist for this step.

1. For each numbered requirement, find the single strongest supporting evidence item in the supplied listing.
2. Cite it by its **exact ref code** — see Section B.
3. Note the connection, and rate the match honestly using the criteria in Section D.
4. Assign a **CV Position** from the supplied slot list — see Section C.
5. Apply the deduplication review in Section E.
6. Where no honest match exists, record the requirement under `gaps` rather than forcing a weak link — see Section F.

---

## B. Reference — cite by exact ref code

Each line of the supplied evidence listing is formatted `[<ref>] (<kind>) <text>`. **The ref code in brackets is what you cite** — nothing else. The kinds you will see, and the shape of their codes:

| Kind (as shown in the listing) | Ref code example | When it applies                                  |
| ------------------------------ | ---------------- | ------------------------------------------------ |
| `STAR action`                  | `5-3`            | Most common — a specific action the candidate took |
| `Responsibility`               | `A-R3`           | A generic role-level responsibility              |
| `Bullet`                       | varies           | A ready-drafted bullet from the Master Bullet Bank |
| `Education`                    | `EDU-3`          | A degree or executive education                  |
| `Language`                     | `LANG-3`         | Language proficiency                             |

**Rules:**

- Cite the ref code **exactly** as it appears in the listing. No table-name prefix, no `>` path, no reformatting.
- Prefer the most specific item available.
- **Never invent a ref code.** A code that is not in the supplied listing is a fabricated citation; it is dropped at the write path and the requirement is left unmapped, so inventing one loses the requirement rather than saving it.

> Historic note (superseded): references used to be written as a table path such as `Tbl_STAR_Actions > Action_ID 5-3`, pointing into `Profile_Reference_Workbook.xlsx`. The ID at the end of that path is the ref code that survives; the path itself no longer addresses anything.

## C. CV Position – Standardized Values

**Use only labels from the `CV POSITION SLOTS` list supplied in your message.** That list is authoritative; it is generated from the CV template's actual slots, so a label outside it binds to no section. The table below explains what each slot is for.

| CV Position                                                       | When to Use                                                            |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Professional Experience - A0. Responsibilities                    | Generic responsibilities for Position A                                |
| Professional Experience - A1. Outsourcing Framework Project       | Any evidence from STAR 5                                               |
| Professional Experience - A2. Governance Transformation Project   | Any evidence from STAR 6                                               |
| Professional Experience - A3. BBAG Wind Down Project              | Any evidence from STAR 7                                               |
| Professional Experience - B0. Responsibilities                    | Generic responsibilities for Position B                                |
| Professional Experience - B1. Accounting Correction Layer Project | Any evidence from STAR 3                                               |
| Professional Experience - B2. Transfer Pricing                    | Any evidence from STAR 4                                               |
| Professional Experience - C1. BBSA Merger Project                 | Any evidence from STAR 2 (Position C has no separate responsibilities) |

## D. Evidence Strength Assessment Criteria

When evaluating how well a piece of evidence supports a specific requirement, use the following criteria:

| Strength       | Definition                                                                 | Guidance |
|----------------|----------------------------------------------------------------------------|----------|
| **Very Strong**    | The evidence directly and specifically demonstrates the core behaviour or outcome described in the requirement. | Prioritise as primary evidence |
| **Strong**         | The evidence clearly shows the required behaviour or skill, even if the context is not perfectly aligned. | Good supporting evidence |
| **Moderate**       | The evidence is related to the requirement but is indirect, partial, or requires interpretation. | Use only when stronger evidence is unavailable |
| **Weak**           | The evidence is tangential or only loosely connected to the requirement. | Generally avoid |

**Rule:** Favour **Very Strong** and **Strong** evidence. Only use Moderate or Weak evidence when no stronger options exist for that requirement.

---

## E. Deduplication and Best-Fit Decision Rules

Each piece of evidence should normally be assigned to **only one requirement** — the one where the connection is strongest and most specific.

**Primary Rule:**
> Assign evidence to the requirement where it demonstrates the **highest relevance and specificity**. Avoid duplicating the same evidence across multiple requirements unless there is a clear and justified reason.

**Decision Hierarchy (apply in this order):**

1. **Specificity** — Choose the requirement that the evidence addresses most directly and specifically.
2. **Priority** — If the evidence fits two requirements with similar strength, assign it to the requirement with the higher priority (**Core > Important > Nice-to-Have**).
3. **Sequence** — If still unclear, assign the evidence to the requirement that appears earliest in the list.
4. **Exception** — Only duplicate evidence across requirements in exceptional cases. Document the reason briefly in the Notes.

**Process Check:**
After the initial mapping, perform a deduplication review and reassign evidence according to the rules above.

---

## F. Handling Requirements with Weak or No Direct Evidence

When a requirement has limited or no strong supporting evidence:

- Be transparent. Do **not** force weak or indirect evidence into the mapping simply to fill a gap.
- Clearly indicate in the output that the requirement has **limited or no direct evidence**.
- Consider whether the gap can be addressed later in the **Profile** section or the **Motivational Letter**.
- Maintain the overall quality of the mapping by avoiding weak evidence.

## G. Persistence

This step emits a single `emit_evidence_map` tool call. The app validates it
(`lib/llm/schemas.ts` → `C2.zod`) and writes one `requirement_tailoring` row per link
(`lib/pipeline/tailoring.ts`), snapshotting the evidence text as `original_text` so a later edit to
the bullet cannot silently rewrite what this mapping was based on. No standalone output, export or
table is produced — do not generate one.

Two fields are **not** yours to set. `approval_status` is the candidate's Keep / Reassign / Drop
verdict and starts `pending`; it is the human gate that decides whether evidence reaches the CV.
`original_text` is copied from the listing you were given, not retyped — cite the ref and the app
carries the text across.

Requirements you could not honestly match go in `gaps`, not in `links`. A gap recorded is a gap the
candidate can act on; a forced weak link is a false claim that reaches the CV.

*Historic (superseded): this step previously produced a SharePoint-ready export — one tab-delimited
row per reference, columns `Lead · Lead:ID · Requirement Order · Rank · Requirement Group ·
Requirement · Requirement Description · Skills · Reference · Original Text · CV Position` — back when
it ran through the Microsoft 365 connector.*

---

### Notes & Quality Rules

- This step must remain **truthful**. Only map a requirement if there is genuine, defensible evidence in the supplied listing.
- Prioritise evidence that is **Very Strong** or **Strong** according to the Evidence Strength Assessment Criteria.
- Apply the Deduplication and Best-Fit Decision Rules to avoid unnecessary duplication across requirements.
- When evidence is indirect or partial, still record it but note the limitation where relevant.
- C2 is the single source of truth for all subsequent tailoring steps (C3 – CV Bullets, C4 – Actual Skills, C5 – Profile).
