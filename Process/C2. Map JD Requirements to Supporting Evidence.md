## Purpose
Map every requirement extracted in Step [[B2. Extract Requirements from Job Description]] to a specific, verifiable evidence from the candidate’s background.
This step creates the traceability foundation required for writing truthful, ATS-optimized CV bullets, Skills and Profile in subsequent steps (C4, C5, and C6).

The result links each Job Description requirement to the exact source of evidence (STAR actions, STAR results, Responsibilities, Bullets, Education, or Languages) and indicates where the corresponding bullet should appear in the CV.

---

## A. Source and Execution Sequence

**You are the deep, targeted pass — not the only pass.** A cheaper initial screen (B6) already
matched every requirement against the Master Bullet Bank and rated each one Excellent / Very
Strong / Good / Weak / No Match. Anything it rated **Excellent or Very Strong is carried forward
automatically and never reaches you** — re-searching a requirement that's already strong doesn't
pay. You only see requirements the initial screen rated **Good, Weak, or No Match**, i.e. the ones
worth digging on. Your job on each is to search the WIDER evidence graph (STAR actions, STAR results
and Responsibilities, not just the curated bullet bank) for something that adds to, or beats, what the
initial screen already found.

Everything this step needs is **supplied inline, in the message you are given**:

- `CANDIDATE EVIDENCE (cite by exact ref code):` — the candidate's whole evidence graph, one line per item, each already labelled with its kind and its stable ref code.
- `CANDIDATE FACTS` (present only when the owner has filled them in at Identity) — fixed eligibility facts: citizenship/work authorization, relocation, travel. These are **not evidence to cite by ref code** — they exist so a requirement that's really an eligibility check ("must have permission to work in the EU", "willing to relocate") is rated honestly against what's actually true, instead of forcing a fabricated bullet-based match or a false No Match.
- `ROLE:` and `REQUIREMENTS (map each by its number):` — the targeted subset only (Good/Weak/No Match), numbered. Each carries an `asking for:` line — its **Requirement Skills**, the JD's own language for what that requirement wants, extracted at [[B2. Extract Requirements from Job Description]] §3.6. Read the requirement and its `asking for:` line **together**: they are one mutually-explaining pair, and the pair is what you are searching evidence against. A requirement may also show `Initial screen found: …` — that is the bar to beat, not a hint to repeat back.
- `CANDIDATE SKILLS, COMPETENCES & ATTRIBUTES` — the candidate's own curated vocabulary (`skills_master`, `star_competences`, `star_attributes`). Not citable as evidence; this is the closed list `mySkills` is drawn from — see §G.
- `CV POSITION SLOTS` — the exact set of labels you may assign.

Do not attempt to open, fetch, or look up a file, a workbook, a SharePoint list, or any other external location — you have no access to one, and nothing outside the supplied text is needed. **The evidence listing you were given is the complete universe of citable evidence:** if something is not in it, it does not exist for this step.

1. For each numbered requirement, find every genuinely supporting evidence item in the supplied listing — several where several honestly apply, not just one. The app already keeps what the initial screen found; you are adding to that, not replacing it wholesale.
2. Cite each by its **exact ref code**, one `links` entry per ref — see Section B.
3. Note the connection, and rate each match honestly using the criteria in Section D.
4. Assign a **CV Position** to each — see Section C.
5. Set **My Skills** on each link, from the candidate's own vocabulary block — see Section G.
6. Apply the deduplication review in Section E.
7. Where no honest match exists at all, record the requirement under `gaps` rather than forcing a weak link — see Section F. A requirement already carrying an initial-screen pick is not a gap just because you found nothing to add.

## B. Reference — cite by exact ref code

Each line of the supplied evidence listing is formatted `[<ref>] (<kind>) <text>`. **The ref code in brackets is what you cite** — nothing else. The kinds you will see, and the shape of their codes:

| Kind (as shown in the listing) | Ref code example | When it applies                                    |
| ------------------------------ | ---------------- | -------------------------------------------------- |
| `STAR action`                  | `5-3`            | Most common — a specific action the candidate took |
| `STAR result`                  | `1-R3`           | A measured OUTCOME of a STAR — what the work produced |
| `Responsibility`               | `A-R3`           | A generic role-level responsibility                |
| `Bullet`                       | varies           | A ready-drafted bullet from the Master Bullet Bank |
| `Education`                    | `EDU-3`          | A degree or executive education                    |
| `Language`                     | `LANG-3`         | Language proficiency                               |

**Rules:**

- Cite the ref code **exactly** as it appears in the listing. No table-name prefix, no `>` path, no reformatting.
- Prefer the most specific item available.
- **Never invent a ref code.** A code that is not in the supplied listing is a fabricated citation; it is dropped at the write path and the requirement is left unmapped, so inventing one loses the requirement rather than saving it.

**`STAR result` — how to read it, and when to prefer it.**

A `STAR result` is the quantified half of a STAR: delivery times, headcounts, cost reductions,
audit findings, assets moved. Its ref code is the parent STAR's number, an `R`, and a sequence
number — `1-R3` is the third recorded result of STAR `1`, the same STAR whose actions are `1-1`
through `1-6`. Note the shape it does NOT have: `A-R3` is a **Responsibility**, because
responsibilities are numbered under a POSITION letter and results under a STAR number. Cite what is
in the brackets and the two never collide.

A result line may carry an indented follow-on line reading `outcome of STAR <n>: <STAR title>`.
That is **context for reading the outcome, not a second citable identity** — it names the work the
outcome came out of, because a result on its own states a consequence with no actor. Cite the ref in
the brackets; never cite the STAR title.

Prefer a result over its parent actions when the requirement asks about **impact, scale, delivery
or outcome** — "delivered X on time", "reduced cost", "passed audit" — because the actions describe
what was done and only the results say what it produced. Prefer the action when the requirement asks
about **method, tooling or how the work was carried out**. Where both honestly apply, cite both:
one `links` entry each, which is what §A.1 already asks for.

> [!Note]
> A second block, `CANDIDATE SKILLS, COMPETENCES & ATTRIBUTES`, follows the evidence listing. Those
> names are **not citable as `evidenceRef`** — a skill is not a piece of evidence, it is what a piece
> of evidence demonstrates. They are the closed vocabulary you draw `mySkills` from; see §G.

> Historic note (superseded): references used to be written as a table path such as `Tbl_STAR_Actions > Action_ID 5-3`, pointing into `Profile_Reference_Workbook.xlsx`. The ID at the end of that path is the ref code that survives; the path itself no longer addresses anything.

## C. CV Position – Standardized Values

**Use only labels from the `CV POSITION SLOTS` list supplied in your message.** That list is authoritative; it is generated from the CV template's actual slots, so a label outside it binds to no section. The table below explains what each slot is for.

| CV Position                                                       | When to Use                                                            |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Professional Experience - A0. Responsibilities                    | Generic responsibilities for Position A                                |
| Professional Experience - A1. Outsourcing Framework Project       | Any evidence from STAR 5                                               |
| Professional Experience - A2. Governance Transformation Project   | Any evidence from STAR 6                                               |
| Professional Experience - A3. BBAG Wind Down Project              | Any evidence from STAR 7                                               |
| Professional Experience - B0. Responsibilities                    | Generic responsibilities for Position B                                |
| Professional Experience - B1. Accounting Correction Layer Project | Any evidence from STAR 3                                               |
| Professional Experience - B2. Transfer Pricing                    | Any evidence from STAR 4                                               |
| Professional Experience - C1. BBSA Merger Project                 | Any evidence from STAR 2 (Position C has no separate responsibilities) |
| Professional Experience - D1. Servicing Center Project            | Any evidence from STAR 1 (Position D has no separate responsibilities) |
| Education                                                         | Any `Education` reference                                              |
| Language                                                          | Any `Language` reference                                               |

Evidence that fits none of the slots is still mappable — leave the position empty rather than forcing a wrong slot. The link is kept and flows into the programmatic CV; it is never dropped for lacking a slot.

## D. Evidence Strength Assessment Criteria

**Use the same 5-band scale the initial screen (B6) uses** — the app compares your rating against
its `Initial screen found:` rating directly, so a second label set would make the two incomparable:

| Strength       | Definition                                                                 | Guidance |
|----------------|----------------------------------------------------------------------------|----------|
| **Excellent**      | The evidence directly and specifically demonstrates the core behaviour or outcome described in the requirement, with a strong outcome attached. | Prioritise as primary evidence |
| **Very Strong**    | The evidence clearly shows the required behaviour or skill, even if the context is not perfectly aligned. | Strong supporting evidence |
| **Good**           | The evidence is related to the requirement but is indirect, partial, or requires interpretation. | Use only when stronger evidence is unavailable |
| **Weak**           | The evidence is tangential or only loosely connected to the requirement. | Generally avoid |
| **No Match**       | Nothing in the listing genuinely supports the requirement. | Record under `gaps`, do not force a link |

**Rule:** Favour **Excellent** and **Very Strong** evidence. Only use Good or Weak evidence when no stronger options exist for that requirement, and rate honestly even when the requirement already carries an initial-screen pick — an honest lower rating simply leaves that pick as the strongest one on file.

## E. Deduplication and Best-Fit Decision Rules

Each piece of evidence should normally be assigned to **only one requirement** — the one where the connection is strongest and most specific.

**Primary Rule:**
> Assign evidence to the requirement where it demonstrates the **highest relevance and specificity**. Avoid duplicating the same evidence across multiple requirements unless there is a clear and justified reason.

**Decision Hierarchy (apply in this order):**

1. **Specificity** — Choose the requirement that the evidence addresses most directly and specifically.
2. **Priority** — If the evidence fits two requirements with similar strength, assign it to the requirement with the higher priority (**Core > Important > Nice-to-Have**).
3. **Sequence** — If still unclear, assign the evidence to the requirement that appears earliest in the list.
4. **Exception** — Only duplicate evidence across requirements in exceptional cases. Document the reason briefly in the Notes.

**Process Check:**
After the initial mapping, perform a deduplication review and reassign evidence according to the rules above.

---

## F. Handling Requirements with Weak or No Direct Evidence

When a requirement has limited or no strong supporting evidence:

- Be transparent. Do **not** force weak or indirect evidence into the mapping simply to fill a gap.
- Clearly indicate in the output that the requirement has **limited or no direct evidence**.
- Consider whether the gap can be addressed later in the **Profile** section or the **Motivational Letter**.
- Maintain the overall quality of the mapping by avoiding weak evidence.

## G. Persistence

This step emits a single `emit_evidence_map` tool call, covering only the targeted (Good/Weak/No
Match) requirements described in Section A. The app validates it (`lib/llm/schemas.ts` → `C2.zod`)
and MERGES your links into `requirement_tailoring` (`lib/pipeline/tailoring.ts`) alongside what it
already carried forward from the initial screen — it does not wipe the table. A link only replaces
a stored row for the same requirement + evidence ref when it rates strictly higher on the Section D
scale; otherwise it is added as another row, or ignored if the ref is already stored. The evidence
text is snapshotted as `original_text` so a later edit to the bullet cannot silently rewrite what
this mapping was based on. No standalone output, export or table is produced — do not generate one.

Two fields are **not** yours to set. `approval_status` is the candidate's Keep / Reassign / Drop
verdict and starts `pending`; it is the human gate that decides whether evidence reaches the CV.
`original_text` is copied from the listing you were given, not retyped — cite the ref and the app
carries the text across.

**`my_skills` — My Skills — IS yours to set, and this is the step that sets it.** Every link you
emit carries a `mySkills` array: which of the candidate's own skills, competences or attributes the
cited evidence demonstrates *for this requirement*. Three rules:

- **Copy names exactly from the `CANDIDATE SKILLS, COMPETENCES & ATTRIBUTES` block.** The app
  validates each one against the real vocabulary and silently drops anything it doesn't recognise —
  the same treatment an invented ref code gets. A near-miss spelling is a dropped skill, not a
  forgiving match.
- **Never restate the JD's wording here.** My Skills is the candidate's own vocabulary. The JD's
  language for the same requirement is `Requirement Skills`, which the app carries onto the row from
  B2 without your involvement.
- **Empty is a valid answer.** If nothing in that block is honestly demonstrated by this evidence,
  emit an empty array. A padded list is the same failure as a forced weak link.

`my_skills` is written to `requirement_tailoring` alongside the link. It is the **traceability
chain** back to the profile — which of the candidate's claimed capabilities this CV line actually
rests on — and it is what [[C4. Transform Evidence into CV Bullets]] is shown when it drafts the
bullet.

*Historic (superseded): the app used to fill `my_skills` itself, by copying the evidence node's own
free-text tags (`star_actions.skills`, `responsibilities.skills`, `bullet_bank.tags`) verbatim —
this step was never asked for a judgement about skills at all, which is why no paragraph described
it. Those tags are graph provenance, not CV vocabulary: 246 distinct names across 104 evidence rows,
180 of them used exactly once, only 8 present in any curated table. Printed verbatim they produced
67 skills in a single CV line. See [[C4 Skills Selection Produces Unreadable Overflow]].*

Requirements you could not honestly match go in `gaps`, not in `links`. A gap recorded is a gap the
candidate can act on; a forced weak link is a false claim that reaches the CV.

*Historic (superseded): this step previously produced a SharePoint-ready export — one tab-delimited
row per reference, columns `Lead · Lead:ID · Requirement Order · Rank · Requirement Group ·
Requirement · Requirement Description · Skills · Reference · Original Text · CV Position` — back when
it ran through the Microsoft 365 connector.*

### Notes & Quality Rules

- This step must remain **truthful**. Only map a requirement if there is genuine, defensible evidence in the supplied listing.
- Prioritise evidence that is **Very Strong** or **Strong** according to the Evidence Strength Assessment Criteria.
- Apply the Deduplication and Best-Fit Decision Rules to avoid unnecessary duplication across requirements.
- When evidence is indirect or partial, still record it but note the limitation where relevant.
- C2 is the single source of truth for all subsequent tailoring steps (C4 – CV Bullets, C5 – Actual Skills, C6 – Profile).
